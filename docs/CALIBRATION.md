# 라이다 보정 및 개발 현황

`LIDAR_SETUP.md` 가 "새 PC에 설치하는 법"이라면, 이 문서는 **"라이다를 놓고 좌표계를 맞추는 법"** 과 **앞으로 만들 것** 을 다룬다.

---

## 1. 보정이 왜 필요한가

시뮬레이션에서는 월드 파일에 좌표를 적으면 라이다가 정확히 거기 놓인다. 대회 설정 파일이 그렇게 생겼다:

```yaml
lidar1_x: 15.0     lidar1_y: -1.5    lidar1_yaw: 1.5708   # 남쪽에서 +y 를 봄
lidar2_x: 15.0     lidar2_y: 21.5    lidar2_yaw: -1.5708  # 북쪽에서 -y 를 봄
```

**실제로는 이렇게 놓을 수 없다.** 줄자로 15 m 를 재도 몇 cm 틀리고, 각도를 90.000° 로 맞추는 것은 불가능하다. 그래서 문제를 뒤집는다.

```
X   라이다를 정확한 위치/각도에 놓으려 애쓴다
O   대충 놓고, 실제로 어디에 어떻게 놓였는지 측정해서 그 값을 파라미터에 적는다
```

파라미터의 `lidar1_x: 15.0` 은 "여기 놓아라"가 아니라 **"여기 놓여 있다"** 는 뜻이다. 실측하면 `14.87`, `1.5382` 같은 값이 들어간다.

### yaw 가 특히 중요하다

위치는 줄자로 재면 되지만 각도는 물리적으로 맞출 수 없다.

```
yaw 오차 1도  ->  10 m 지점에서 17 cm 어긋남
yaw 오차 5도  ->  10 m 지점에서 87 cm 어긋남
```

채점 기준이 수평오차 0.5 m 라면 yaw 는 **1~2도 안**으로 잡아야 한다. 사람이 서서 방향을 확인하는 정도(±22.5도)로는 턱없이 부족하다.

## 2. 두 가지 보정 방식

| | **(A) 마커가 좌표계를 만듦** | **(B) 좌표계가 이미 있음** |
|---|---|---|
| 상황 | 실내 실험, 빠른 세팅 | **대회** |
| 마커 개수 | 2개 | 3개 이상 |
| 마커 좌표 측정 | **불필요** | 필요 |
| 오차 검증 | 안 됨 | 잔차로 확인 가능 |
| 구현 상태 | **완료** | 미구현 |

### (A) 원리 — 마커 2개가 곧 좌표계

```
    M2 ●
        \
          \   이 방향이 +x 가 된다
            \
              ● M1     여기가 (0, 0) 이 된다

         [] 라이다 (어디에 어떻게 놓여 있든 상관없음)
```

맞춰야 할 정답이 없다. **놓은 자리가 곧 정답**이므로 배치 오차라는 개념 자체가 없다. 줄자도 각도기도 필요 없고, M2 까지의 거리도 상관없다(방향만 쓴다).

### (B) 원리 — 알려진 좌표로 라이다를 찾음

```
마커를 (3,3), (6,9), (9,15) 에 놓는다   <- 좌표를 이미 아는 지점
라이다가 본 좌표와 대조해 라이다 자세를 푼다
```

원점에는 **아무것도 놓지 않는다.** 마커 좌표를 아니까 원점은 자동으로 따라온다. 같은 마커를 두 라이다가 다 보면 **두 라이다가 자동으로 정렬**된다.

## 3. 마커 — 원기둥을 쓰는 이유

라이다는 물체의 **자기 쪽 면만** 본다. 그래서 점들의 median 을 중심으로 쓰면 실제 중심보다 라이다 쪽으로 **반지름만큼** 치우친다.

원기둥은 이 편향을 없앨 수 있다. 보이는 호에 반지름을 아는 원을 맞추면 가려진 뒤쪽까지 포함한 진짜 중심이 나온다.

### 합성 데이터 검증

| 조건 | 단순 median | 원 피팅 | 개선 |
|---|---|---|---|
| r=0.15, 3 m | 112.7 mm | **4.0 mm** | 28배 |
| r=0.15, 8 m | 105.3 mm | **9.2 mm** | 11배 |
| r=0.25, 3 m | 185.8 mm | **2.1 mm** | 88배 |

median 오차가 정확히 반지름만큼 나오는 것이 보인다 — 이론대로다.

### 반지름은 고정해야 안정적이다

| | 반지름도 추정 | 반지름 고정 |
|---|---|---|
| x 흔들림 | ± 47.4 mm | **± 8.4 mm** |
| y 흔들림 | ± 79.7 mm | **± 10.8 mm** |

미지수가 3개 -> 2개로 줄어서 5~7배 안정된다.

### 반지름 추정을 믿으면 안 된다 — 실제로 당한 것

첫날 물통 반지름을 라이다로 추정해 **0.108 m (지름 21.6 cm)** 를 얻었다.
그런데 오차가 **± 84 mm** 였다. 반지름과 맞먹는 오차다.

이튿날 다시 재니 **0.047 m (지름 9.4 cm)** 가 나왔고, 줄자로 확인한 결과
**9.4 cm 가 맞았다.** 첫날 값은 두 배 넘게 틀렸다.

이것이 왜 문제인가: 원 피팅은 보이는 호 **뒤로 반지름만큼** 중심을 놓는다.
반지름이 61 mm 크면 중심이 라이다 반대쪽으로 61 mm 밀린다.

```
첫날 보정: M1, M2 중심이 각각 61 mm 씩 밀린 상태
        -> 원점 위치에 61 mm 계통 오차
        -> yaw 에도 약 0.67도 기여
```

**"흔들림이 작다"와 "정확하다"는 다르다.** 첫날 반지름을 0.108 로 고정한 뒤
흔들림은 ±8 mm 로 줄었지만, 그것은 같은 틀린 값을 반복해서 쓴 결과일 뿐이다.

같은 이유로 "원점-라이다 거리가 세 번 다 2.4176~2.4188 m 로 일치했다"는 것도
**정확도의 근거가 아니다.** 같은 반지름을 세 번 썼으니 같은 값이 나온 것이다.
반복정밀도만 보여줄 뿐이다.

### 그래서 — 지름은 줄자로 재서 넣는다

```bash
ros2 run dual_ouster_driver calibrate --ros-args -p marker_radius:=0.047
```

값을 주면 추정 단계를 건너뛴다. **높이나 각도와 달리 지름은 줄자로 정확히
잴 수 있다.** 라이다에게 물어볼 이유가 없다.

### 마커 고를 때

- **진짜 원통**이어야 한다. 라바콘처럼 테이퍼지면 높이마다 중심이 달라져 피팅이 어긋난다
- **크기가 정확도를 좌우한다.** 20 m 에서 쓰려면 지름 40~50 cm 는 되어야 한다. 가까이(5~15 m) 두면 25~30 cm 로 충분하다
- 거푸집 지관(콘크리트 기둥용 종이관)이 가성비가 좋다 — 싸고 가볍고 완벽한 원통
- **수직으로 세워야 한다.** 기울면 원 피팅이 틀어진다

### 마커 간격이 yaw 정확도를 결정한다

```
마커 위치 오차 2 cm, 간격  2 m  ->  0.57도
마커 위치 오차 2 cm, 간격  5 m  ->  0.23도
마커 위치 오차 2 cm, 간격 10 m  ->  0.11도
```

**마커는 최대한 멀리 벌린다.** 이것이 정확도를 올리는 가장 값싼 방법이다.

## 4. 보정 실행

### 4.1 자동 — `calibrate` (권장)

아래 4.2~4.7 의 모든 단계를 대화형으로 진행하고 YAML 까지 써준다.
손계산이 없으므로 실수할 여지가 적다.

```bash
# 드라이버 먼저
ros2 launch dual_ouster_driver dual_os1.launch.py

# 보정 (다른 터미널)
ros2 run dual_ouster_driver calibrate --ros-args -p front_axis:=+y
```

```
[1/5] 정면 방향     라이다 주변 비우고 Enter -> 정면에 서서 Enter
[2/5] 설치 높이     자동 (바닥 z 최빈값)
[3/5] 마커 반지름   마커 놓고 Enter -> 지름과 원기둥 여부 검증
[4/5] 원점 지점     마커 놓고 Enter
[5/5] 축 방향 지점  마커 옮기고 Enter
      벽 탐색       비우고 Enter
      -> config/calibration_lidarN.yaml 저장
```

주요 옵션:

| 옵션 | 뜻 |
|---|---|
| `-p front_axis:=+y` | 최종 좌표계에서 라이다 정면이 향할 축 (`+x`/`+y`/`-x`/`-y`) |
| `-p skip_front_check:=true -p yaw_base:=180.0` | 정면 방향을 이미 알 때 사람이 서는 단계 생략 |
| `-p lidar_id:=2` | 2번 라이다 (`/lidar2/points`, `calibration_lidar2.yaml`) |
| `-p n_frames:=40` | 측정에 쓸 프레임 수. 늘리면 안정적, 대신 오래 걸림 |

`calibrate` 는 `/lidarN/points` 를 직접 구독하므로 `roi_filter` 를 기준 좌표계로
되돌리는 준비 단계가 필요 없다.

### 4.2 수동 — 개별 노드로 (문제가 생겼을 때)

`calibrate` 가 어느 단계에서 막히면 아래 노드를 하나씩 돌려 원인을 좁힌다.

#### 준비

```bash
# 드라이버
ros2 launch dual_ouster_driver dual_os1.launch.py

# 기준 좌표계로 ROI (yaw 180 = 라이다 정면이 +x, 원점 = 라이다)
ros2 run dual_ouster_driver roi_filter --ros-args \
  -p lidar_z:=0.84 -p yaw_deg:=180.0 -p origin_x:=0.0 -p origin_y:=0.0 \
  -p roi_x_min:=-0.5 -p roi_x_max:=4.4 -p roi_y_min:=-2.2 -p roi_y_max:=2.2 \
  -p roi_z_min:=0.045 -p roi_z_max:=0.60

# 마커 검출 (반지름은 1단계에서 알아낸 값)
ros2 run dual_ouster_driver marker_fit --ros-args \
  -p radius:=0.108 -p n_average:=20 \
  -p z_min:=0.045 -p z_max:=0.60 \
  -p min_points:=12 -p min_samples:=4 -p max_span:=0.45
```

#### 라이다 정면 방향 확인

문서만 보고 추측하면 틀린다. 반드시 사람이 서서 확인한다.

```bash
ros2 run dual_ouster_driver axis_probe
```

정면이라 생각하는 위치에 1 m 앞에 10초 서 있으면, 거리가 급감하고 점이 폭증한 방향이 나온다. 이 설치에서는 **정면이 프레임의 -x** 였다(그래서 `yaw_deg` 기본값 180).

> **Ouster 좌표계:** Sensor frame 은 +x 가 커넥터 쪽, Lidar frame 은 그것을 z축으로 180도 돌린 것. 드라이버는 `point_cloud_frame == sensor_frame` 일 때만 변환을 적용하므로(`os_static_transforms_broadcaster.h`), 지금 설정은 **Lidar frame** 이다.
>
> **프레임을 바꿔도 찍히는 내용은 같다.** 두 프레임 차이는 회전과 오프셋뿐이다. 특정 방향을 안 찍으려면 프레임이 아니라 센서의 `azimuth_window` 를 좁혀야 한다.

#### 설치 높이

```bash
ros2 run dual_ouster_driver room_survey
```

바닥 점의 z 최빈값으로 구한다. 벽 위치와 추천 ROI 도 같이 나온다.

> **수직 사각지대:** 수직 시야각이 ±21.2도라 높이 0.84 m 설치 시 발밑 반경 약 2.2 m 바닥은 원리적으로 안 보인다. RViz 탑뷰에서 가운데가 원형으로 뚫려 보이는 것은 정상이다. 낮은 물체(높이 15 cm)는 **1.9 m 이상 떨어져야** 보인다.

#### 두 지점 기록

```bash
# 1) 원점 삼을 자리에 마커를 놓고
ros2 service call /marker_fit/record std_srvs/srv/Trigger

# 2) +x 방향 자리로 옮기고
ros2 service call /marker_fit/record std_srvs/srv/Trigger
```

**M2 는 M1 에서 라이다 정면 방향으로 곧게 밀어야 한다.** 좌우로 어긋나면 축이 기운다.

```
2 m 벌렸는데 좌우 10 cm 어긋남  ->  축 2.9도 기울어짐
```

축이 기울면 **쓸 수 있는 영역이 줄어든다.** 실측 사례:

| 축 기울기 | 사용 가능 면적 |
|---|---|
| 65도 (M2 를 대각선에 둠) | 11.0 / 20.6 m² = **53%** |
| 3.3도 (정면으로 밀음) | 18.0 / 20.6 m² = **87%** |

회전된 좌표계에서는 방이 마름모꼴로 보여 축정렬 ROI 박스가 안 맞기 때문이다.

#### 계산과 적용

```bash
ros2 run dual_ouster_driver pose_solve --ros-args -p current_yaw_deg:=180.0
```

```
  보정량
    회전 +3.312도
  적용할 값
    -p yaw_deg:=183.312
    -p origin_x:=1.5471
    -p origin_y:=1.8577
  적용 후 라이다 위치
    (-1.5471, -1.8577)   원점에서 2.4176 m
  검증 (적용 후 마커 위치)
    M1 -> ( 0.0000,  0.0000)   기대 (0, 0)
    M2 -> ( 2.0630,  0.0000)   기대 (2.0630, 0)
```

`pose_solve` 는 **정면 = +x** 기준으로 내놓는다. 정면을 다른 축으로 쓰려면:

| 원하는 정면 | yaw 보정 | origin 보정 |
|---|---|---|
| +x | 그대로 | 그대로 |
| **+y** | **+90** | **+90도 회전** |
| -x | +180 | +180도 회전 |
| -y | -90 | -90도 회전 |

대회 `lidar1` 은 `yaw=+90도`로 **+y 를 바라본다.** 그 형태를 쓰려면 +y 로 맞춘다.

### 4.3 검증 — 무엇을 믿을 수 있나

`calibrate` 는 끝에 검증을 출력한다.

```
  M1 -> (+0.0000, +0.0000)   기대 (0, 0)
  M2 -> (+0.0000, +2.0600)   기대 (0, 2.0600)
  잔차 0.0000 mm  정상
```

**이 잔차는 계산이 맞는지만 본다.** 측정이 정확한지는 말해주지 않는다.
M1 이 원점으로 가는 것은 정의상 당연하기 때문이다.

측정 정확도를 보려면 두 가지를 나눠 봐야 한다.

| | 무엇을 보는가 | 어디서 나오나 |
|---|---|---|
| **반복정밀도** | 같은 것을 여러 번 재면 얼마나 같은가 | 마커 흔들림 / 마커 간격 |
| **계통 오차** | 값 자체가 치우쳐 있지 않은가 | 반지름이 맞는지 (줄자) |

반복정밀도는 출력에 나오지만, **계통 오차는 마커 지름을 실측해야만 알 수 있다.**

## 5. 계산 원리 — 원시 점군에서 보정값까지

보정 결과로 나오는 `lidar_z`, `yaw_deg`, `origin_x/y` 가 각각 라이다의 어떤
데이터에서 어떤 계산을 거쳐 나오는지 정리한다.

### 5.1 라이다가 실제로 주는 것

OS1-128 은 `1024 x 128` 격자로 **거리**를 잰다. 드라이버가 이걸 직교좌표로
바꿔 `PointCloud2` 로 내보낸다.

```
한 프레임 = 1024 (수평) x 128 (수직) = 131,072 점,  초당 10 프레임
점 하나   = (x, y, z) float32,  단위 m,  원점 = 라이다 광학 중심
```

원시 좌표계(`lidar1` 프레임)는 **라이다 자신**이 기준이다.

```
z = 0     라이다가 달린 높이       -> 바닥은 z 가 음수
x, y      라이다 몸통 기준 수평면   -> 정면이 어느 축인지는 설치하기 나름
```

보정이 하는 일은 이 **라이다 기준 좌표를 방 기준 좌표로 바꾸는 회전 + 이동**
두 개를 알아내는 것이다. 그래서 미지수는 딱 세 개다 — `lidar_z`(높이),
`yaw_deg`(회전), `origin_x/y`(이동).

각도 분해능은 수평 0.0061 rad, 수직 0.0058 rad 이다. 즉 **점 사이 간격 ≒
0.006 x 거리**로, 5 m 앞에서 3 cm, 10 m 앞에서 6 cm 다. 뒤에 나오는 정확도는
전부 이 숫자에서 갈린다.

### 5.2 `lidar_z` — 설치 높이

바닥은 방 안에서 가장 크고 평평한 면이라, **바닥 점들의 z 최빈값**이 곧
`-(설치 높이)` 다. 평균이 아니라 최빈값을 쓰는 이유는 고리 안에 의자나
사람 발이 섞여도 봉우리는 바닥에 그대로 남기 때문이다.

문제는 **어디를 봐야 바닥인가**이다. 수직 시야가 ±21.2도 라서 발밑은 원리적으로
안 보인다.

```
사각지대 반경 = 높이 / tan(21.46도)      0.8 m -> 2.1 m,   2.0 m -> 5.1 m
```

높이를 모르는 상태에서 사각지대를 계산해야 하는 순환이 생긴다. 그래서 두 번
돌린다 (`measure_floor`).

```
1차   반경 0.5 ~ 60 m 의 아래쪽 점 전체로 대충 h0 를 잡는다
2차   blind = h0 / tan(21.46도)
      반경 blind*1.15 ~ blind*4.0 고리만 다시 보고 최빈값 -> 최종 높이
```

2차에서 고리를 **높이에 맞춰 바깥으로 옮기는** 것이 핵심이다. 고정 고리를
쓰면 라이다를 2 m 로 올렸을 때 고리가 통째로 사각지대에 들어가 실패한다.

최빈값은 히스토그램 봉우리로 찾는다.

```python
r    = hypot(x, y)
ring = pts[(r > lo) & (r < hi)]      # 사각지대 밖 고리
lo_z = ring[ring.z < -0.05]          # 라이다보다 아래
h    = -mode_z(lo_z)                 # 40구간 히스토그램 최대 칸의 중앙
```

> 바닥이 기울어 있거나 고리 안에 바닥이 안 보이면(벽이 가까움) 자동 측정이
> 틀린다. 그럴 때는 줄자로 재서 `-p lidar_z:=1.85` 로 직접 넣는다.

### 5.3 마커 중심 — 앞면만 보고 진짜 중심 찾기

한 마커의 중심 `(cx, cy)` 하나를 뽑는 데 다섯 단계를 거친다. 매 프레임
13만 점에서 시작해 마커 점 수십 개까지 좁힌다.

**(1) 좌표 예비 변환** — 아직 방 좌표는 모르지만, 정면 확인 단계에서 얻은
`yaw_base` 와 방금 잰 `lidar_z` 로 "라이다 정면이 +x, 바닥이 z=0" 인 임시
좌표계를 만든다. 이후 단계의 숫자를 사람이 이해할 수 있게 하려는 것이다.

```python
q[:, :2] = q[:, :2] @ rot2(yaw).T      # 회전
q[:, 2] += lidar_z                     # 바닥이 z=0 이 되게 올림
```

**(2) 정면 직사각형** — 마커는 사람이 라이다 앞에 놓았으니 뒤나 먼 곳에 있을
리 없다. 정면 방향 `fwd`, 좌우 `side` 로 잘라낸다.

```python
q = q[(fwd > 0) & (fwd <= search_fwd_max) & (abs(side) <= search_side_max)]
                                       # 기본 앞 4 m, 좌우 ±2 m
```

`fwd > 0` 이 정면 반쪽을 만들고 거기에 사각 한계를 씌우므로, **결과는 반원이
아니라 직사각형**이다.

**(3) 사람이 찍은 자리 주변** — 화면에서 대략적인 위치를 입력받아 그 반경
(`search_radius`, 기본 0.5 m) 안만 남긴다. 이게 배경을 지우는 대신 쓰는
방법이다.

> 초기에는 배경 차분(빈 방을 먼저 찍고 빼기)을 썼는데, 마커 점이 17개까지
> 깎여 반지름이 0.049 로 망가졌다. **ROI 로 주변을 먼저 잘라내는 쪽이
> 확실히 낫다.**

**(4) 그 자리의 바닥 높이를 재서 위만 남김** — 바닥은 거리에 따라 보였다
안 보였다 하고 완전히 평탄하지도 않다. 고정 z 창 대신 **이 자리의 실제
바닥**을 재고 그 위 `ground_clear` 만큼부터 본다.

```python
low = q[q.z < 0.25]
if len(low) >= 30:
    floor = 히스토그램(low.z, 40구간) 최대 칸의 중앙
    zmin  = max(marker_z_min, floor + ground_clear)
q = q[q.z >= zmin]
```

**(5) DBSCAN + 원 맞춤** — 남은 점을 `eps` 안에서 군집화하고, 각 군집의 XY 에
원을 맞춘다.

여기가 **surface bias 를 없애는 지점**이다. 라이다는 마커의 **앞면 호만** 본다.
그 점들의 median 을 쓰면 중심이 라이다 쪽으로 **반지름만큼** 치우친다.
지름 30 cm 기둥이면 15 cm 오차다. 원을 맞추면 가려진 뒷면까지 포함한 진짜
중심이 나온다.

```
1) Kåsa 대수해 — 선형 최소자승으로 초기값
   x² + y² = 2·cx·x + 2·cy·y + (r² - cx² - cy²)   를 [cx, cy, c] 에 대해 풀면 선형

2) 기하 잔차 최소화 — least_squares 로 다듬기
   잔차 = hypot(x-cx, y-cy) - r          <- 점에서 원까지의 실제 거리
```

**반지름은 줄자로 잰 값으로 고정한다.** 미지수가 3개에서 2개로 줄어 훨씬
안정적이다. 짧은 호에서 반지름을 자유롭게 추정하면 원의 크기와 중심 위치가
서로를 상쇄해서, 잔차는 작은데 중심은 크게 틀리는 답이 나온다.

| | 반지름 자유 | 반지름 고정 |
|---|---|---|
| r=0.15, 8 m 에서 중심 오차 | 105.3 mm | **9.2 mm** |
| x 흔들림 | ± 47.4 mm | **± 8.4 mm** |

> 이걸 무시했다가 첫날 반지름을 0.108 로 추정했고(실제 0.047), 원점에
> 61 mm 계통 오차가 생겨 그날 보정값을 통째로 버렸다.

**(6) 여러 프레임 묶기** — `n_frames`(기본 25) 만큼 반복하면 후보가 여러 개
쌓인다. 위치로 다시 DBSCAN(`eps=0.30`) 해서 물체별로 묶고, 각 묶음에서
중앙값에서 `3 x (중앙 거리)` 넘게 벗어난 프레임을 버린 뒤 평균낸다.

```
최종 중심 = 살아남은 프레임들의 (cx, cy) 평균
sx, sy    = 그 표준편차   <- 이게 곧 반복정밀도
```

### 5.4 `yaw_deg` 와 `origin` — 마커 2개가 좌표계를 정의한다

마커 두 개의 중심 `P1`, `P2` 를 위에서 구했다. 여기서 규칙은 단순하다.

```
P1 이 있던 자리  ->  원점 (0, 0)
P1 -> P2 방향    ->  지정한 축 (+y)
```

미지수는 회전 `θ` 하나와 이동 `origin` 하나다.

```python
dv     = P2 - P1
target = FRONT_AXIS_ROT['+y']                      # = 90도
θ      = target - degrees(atan2(dv.y, dv.x))       # dv 를 목표 축으로 돌리는 각
yaw    = yaw_base + θ
origin = rot2(θ) @ P1                              # 회전 후 P1 이 있는 자리
```

`roi_filter` 는 이 두 값으로 매 프레임을 변환한다. 순서가 중요하다 —
**돌리고 나서 빼야 한다.**

```python
pts[:, :2] = pts[:, :2] @ rot2(yaw).T - origin
pts[:, 2] += lidar_z
```

넣어보면 `P1 -> (0,0)`, `P2 -> (0, |P2-P1|)` 이 나온다. 이 검증의 잔차는
**계산이 맞는지만** 보는 것이고, 측정이 정확한지는 말해주지 않는다.

**라이다 위치**는 덤으로 나온다. 방 좌표에서 원점의 반대편이다.

```python
lidar_xy = rot2(yaw) @ [0, 0] - origin = -origin
```

### 5.5 왜 마커 2개면 충분한가

평면 위 강체변환의 자유도는 3개다 — 회전 1, 이동 2. 마커 하나는 방정식 2개를
주므로 두 개면 4개, 3개보다 많아 충분히 결정된다. 남는 1개는 **거리 확인**에
쓰인다. 계산된 `|P2-P1|` 이 줄자로 잰 값과 다르면 무언가 틀린 것이다.

z 축(회전 2개, 이동 1개)은 **바닥이 수평**이라는 가정으로 해결한다. 그래서
`lidar_z` 하나만 재면 된다. 바닥이 기울어 있으면 이 가정이 깨지고, roll/pitch
까지 풀어야 한다 — 지금은 하지 않는다.

### 5.6 `yaw` 정확도는 마커 간격이 좌우한다

각도 오차는 **위치 오차를 간격으로 나눈 값**이다.

```
yaw 오차(rad) ≒ 마커 위치 오차 / 마커 간격
```

| 마커 간격 | 위치 오차 8 mm 일 때 yaw 오차 | 20 m 끝에서의 위치 오차 |
|---|---|---|
| 1 m | 0.46도 | 160 mm |
| 2 m | 0.23도 | 80 mm |
| 5 m | 0.09도 | 32 mm |
| 10 m | 0.05도 | 16 mm |

**yaw 오차는 거리에 비례해 커진다.** 라이다 앞 2 m 에서 잘 맞아도 20 m 에서는
10배로 벌어진다. 그래서 **마커는 최대한 멀리 떨어뜨려 놓아야 한다.**
실측 보정(간격 2.06 m)의 yaw 반복정밀도는 0.077도 였다.

### 5.7 비행 중 위치 — `cluster_median`

보정이 끝나면 같은 변환이 매 프레임에 적용되고, 그 뒤는 훨씬 단순하다.

```
roi_filter        회전 + 이동 + ROI 상자로 자르기   13만 점 -> 수십~수백 점
cluster_median    DBSCAN -> 가장 큰 군집 -> median
flight_recorder   칼만필터(등속도 6상태) + CSV 기록
```

여기서는 **원 맞춤을 쓰지 않는다.** 드론은 원기둥이 아니고 자세가 계속 바뀌어서
맞출 모양이 없다. 대신 median 을 쓴다 — 평균은 군집에 섞인 이상점 하나에
끌려가지만 median 은 거의 움직이지 않는다.

**즉 비행 중 위치에는 surface bias 가 남아 있다.** 드론 크기의 절반쯤,
라이다 쪽으로 치우친다. 텔로(10 cm)면 5 cm 미만이라 무시할 만하고, 50 cm
기체면 20 cm 가 넘어 무시할 수 없다. 라이다 2대를 서로 마주보게 놓으면
치우침이 반대 방향이라 평균으로 상당 부분 상쇄된다.

시각은 처리 시각이 아니라 **라이다가 찍은 시각**을 그대로 물려준다. 현재
끝단 지연이 약 215 ms 인데, 처리 시각으로 덮으면 그게 통째로 오차가 된다.

## 7. 이번에 고친 것

### 7.1 DDS 전송 — 프레임 대량 유실

포인트클라우드 한 프레임이 약 2 MB 다. 기본 설정에서 Fast DDS 는 같은 PC 안에서도 UDP 로 보내는데, 2 MB 는 UDP 패킷 약 1400 개로 쪼개진다. 조각 하나만 잃어도 메시지 전체가 버려진다.

```
기본 설정        평균  3.5 Hz,  간격 편차 398 ms
SHM + 큰 버퍼    평균 10.0 Hz,  간격 편차 0.5 ms
```

**CPU 는 문제가 아니었다.** 전체 파이프라인이 코어의 41%(8스레드 중)만 쓰고 있었고 CPU 는 94% 유휴였다. 컴퓨터를 늘리거나 좋은 것을 써도 똑같이 유실됐을 것이다.

`config/fastdds_large.xml` 를 만들고 `~/.bashrc` 에 등록했다.

```bash
export FASTRTPS_DEFAULT_PROFILES_FILE=$HOME/ros2_ws/src/dual_ouster_driver/config/fastdds_large.xml
```

### 7.2 roi_filter — 원점 이동 지원

`origin_x`, `origin_y` 파라미터를 추가했다. 회전을 적용한 **뒤에** 뺀다.

```python
pts[:, :2] = pts[:, :2] @ self._rot.T - self.origin
pts[:, 2] += self.lidar_z
```

파라미터를 매 프레임 다시 읽으므로 **재시작 없이 `ros2 param set` 으로 조절**된다.

### 7.3 marker_fit — 원기둥 선택과 이상값 제거

- 처음에는 "가장 큰 클러스터"를 골랐는데, ROI 를 넓히니 벽을 잡았다(잔차 247 mm). **크기로 먼저 거르고, 남은 것 중 원 피팅 잔차가 가장 작은 것**을 고르도록 바꿨다
- 배치의 약 10%에서 다른 물체를 골라 튀었다(±300 mm). **중앙값에서 벗어난 프레임을 제외**하고 평균을 내도록 했다
- `record` 서비스가 **흔들림이 크면 저장을 거부**한다(기본 30 mm 초과 시)

### 7.4 진단 계측 추가

`roi_filter` 와 `cluster_median` 에 처리시간/입력주기/지연을 넣었다.

```
20프레임: 124086 -> 0점 (0.0%)  |  처리 11.8/14.0ms  |  입력 10.0Hz  |  지연 203/204ms
```

이것으로 DDS 유실 문제를 찾아냈다.

토픽에도 그대로 쓸 수 있다.

느린 것인지 받는 쪽이 밀리는 것인지 가리려면 `roi_filter` 로그의
`입력 10.0Hz | 지연 203ms` 를 같이 본다.

### kill -9 후에는 정리가 필요하다

Fast DDS 공유메모리 찌꺼기가 남고 ROS 데몬 그래프가 깨진다. `ros2 lifecycle get` 이 `Node not found` 를 내면서 `ros2 topic info` 는 정상으로 나오는 모순이 생긴다.

```bash
pkill -9 -f 'os_driver|roi_filter|cluster_median|dual_os1.launch'
sleep 2
rm -f /dev/shm/fastrtps_* /dev/shm/sem.fastrtps_*
ros2 daemon stop
```

### 타임스탬프는 QoS 와 무관하지만, 덮어쓰면 안 된다

**QoS 는 배달 방식이지 내용물이 아니다.** Best Effort 라 메시지가 유실될 수는 있어도,
도착한 메시지의 스탬프는 정확하다. 유실은 기록에 구멍으로 남을 뿐이다.

정작 문제였던 것은 파이프라인 끝에서 스탬프를 덮어쓰던 코드다.

```
드라이버        header.stamp = 촬영 시각          O
roi_filter      header.stamp = msg.header.stamp   O  그대로 전달
cluster_median  stamp = now()                     X  현재 시각으로 덮음  <- 고침
```

처리를 마친 시각(약 215 ms 후)을 찍고 있었다. 사후 분석에서는 이것이 그대로 오차가 된다.

```
2 m/s 이동 중  ->  215 ms x 2 = 43 cm
```

**노드를 새로 만들 때는 반드시 입력 메시지의 스탬프를 물려줘야 한다.**

### 스탬프는 프레임의 한 시점일 뿐이다

라이다는 한 바퀴에 100 ms 걸린다. 프레임 하나 안의 점들은 **최대 100 ms 시간차**가 있고
`header.stamp` 는 그중 한 시점이다.

```
2 m/s 이동  ->  100 ms 안에 20 cm 이동
```

호버 중이면 무관하고, 빠르게 나는 구간에서만 문제가 된다. 정밀하게 하려면 포인트마다
있는 `t` 필드(스캔 내 오프셋)를 써야 하는데, 지금은 `point_type: 'xyz'` 라 받지 않고 있다.

### 시계 기준 — TIME_FROM_ROS_TIME

지금 설정은 **드라이버가 패킷을 받은 호스트 시각**을 찍는다. 레이저 발사 시각보다
1 ms 정도 뒤지만 실용적으로는 무시할 수준이다.

라이다 2대를 **같은 PC** 에 물리면 시계가 하나라 서로 비교 가능하다. 노트북 2대로 나누면
시계가 달라져 chrony 나 PTP 가 필요해진다. `TIME_FROM_PTP_1588` 로 바꾸면 센서가 직접
찍어주므로 호스트 시계와 무관해진다(두 라이다가 같은 스위치에 물려 있어야 함).

### 표적 크기가 파라미터를 좌우한다

같은 설정으로 사람은 잘 잡히는데 텔로 드론이 안 잡혔다. 복셀 5 cm 가 원인이었다.

```
텔로 10x9x4 cm  ->  5cm 격자에 최대 4 복셀   ->  min_points=10 을 절대 못 넘음
사람 45x170 cm  ->  1000 복셀 이상          ->  문제 없음
```

거리별 원본 점 개수:

| 거리 | 텔로 | 50cm급 드론 | 사람 |
|---|---|---|---|
| 2 m | 24 | 1025 | 5217 |
| 3 m | 10 | 432 | 2256 |
| 5 m | 3 | 160 | 840 |
| 8 m | 0 | 60 | 315 |

**텔로 탐지 한계는 5~6 m.** 대회 기체(50 cm급)는 20 m 까지 가능하다.

텔로용 설정:

```bash
ros2 run dual_ouster_driver cluster_median --ros-args \
  -p voxel_size:=0.0 -p min_points:=4 -p min_samples:=3 -p max_span:=0.6
```

### 9.3 `track.csv` 열

```
t_sec        라이다가 찍은 시각 (첫 프레임 = 0). 처리 시각이 아니다
detected     1/0.  0 이면 그 프레임엔 아무것도 못 잡았다
raw_x/y/z    cluster_median 이 낸 median 좌표 그대로
kf_x/y/z     칼만필터를 거친 값
kf_vx/vy/vz  속도 (필터가 추정)
speed        속도 크기
n_cluster    그 프레임에서 살아남은 군집 개수
```

**원본과 칼만을 둘 다 남긴다.** 어느 쪽이 나은지는 데이터를 보고 판단한다.
필터는 튀는 걸 눌러주지만 급기동은 뒤늦게 따라간다.

### 9.4 왜 rosbag 도 같이 남기나

CSV 만 남기면 **그때의 파라미터로 계산된 결과가 전부**다. 비행 후에
"왜 30초에 끊겼지", "`min_points` 를 낮췄으면 잡혔을까" 를 확인할 방법이 없다.
원본을 남겨두면 **날린 건 한 번이고 분석은 몇 번이든 다시 한다.**

| 토픽 | 용량 | 나중에 바꿔볼 수 있는 것 |
|---|---|---|
| `/lidar1/points` | 약 20 MB/s | ROI, 보정값, 바닥컷, DBSCAN — 전부 |
| `/lidar1/roi_points` | 약 16 KB/s | DBSCAN 파라미터만 |

5분 비행이면 원본 약 6 GB 다. 디스크가 빠듯하면 `bag:=roi`, 정말 급하면
`bag:=none` 으로 끈다. **보정값을 의심할 상황이라면 반드시 `raw` 가 있어야 한다.**

되감아 다시 돌리려면:

```bash
ros2 bag play ~/flights/bag_20260823_200023_test1
# 다른 터미널에서 roi_filter/cluster_median 을 파라미터만 바꿔 다시
```

### 9.5 리포트가 말해주는 것과 말해주지 않는 것

요약에 나오는 값들:

```
검출률          전체 프레임 중 몇 %에서 표적을 잡았나
놓친 구간       언제 몇 초 놓쳤나 (가장 긴 구간이 제일 중요하다)
이동 범위       x/y/z 최소~최대, 이동 거리 합계
속도            평균/중앙값/최대/95백분위
원본 vs 칼만    두 값의 차이 — 크면 관측이 튀었거나 필터가 과하게 눌렀다
호버 구간       속도 0.15 m/s 이하로 1초 이상 머문 구간과 그 퍼짐
```

**기준값(ground truth) 이 없으므로 정확도는 평가할 수 없다.** 이 수치는
"라이다가 무엇을 봤는가" 이지 "그게 맞는가" 가 아니다. 호버 구간의 "퍼짐"만이
정확도의 간접 지표다 — 드론이 실제로 가만히 있었다면 그 퍼짐이 곧 측정 잡음이다.

> 실내에서는 모캡으로 기준값을 잡을 예정이다. 붙이면 같은 형식으로 `truth.csv`
> 를 남기고 `flight_report` 가 비교하게 하면 된다.

### 9.6 표적이 작으면 파라미터를 낮춰야 한다

`record_flight.launch.py` 는 텔로 같은 작은 기체 기준으로 잡아 두었다.

```
voxel_size   0.0    복셀을 켜면 점 수십 개짜리 표적이 통째로 사라진다
min_points   4      멀리 있는 텔로는 4~6점밖에 안 잡힌다
min_samples  3
max_span     1.5    이보다 크면 벽 잔재로 본다
```

점 개수는 거리로 정해진다 — **점 간격 ≒ 0.006 x 거리**.

| 표적 | 5 m | 10 m | 20 m |
|---|---|---|---|
| 텔로 (10 cm) | 약 9점 | 약 2점 | 못 봄 |
| 50 cm 기체 | 약 200점 | 약 60점 | 약 15점 |

텔로는 5~6 m 가 한계다. 50 cm 기체면 20 m 까지 간다.

### 9.7 잘 안 될 때

| 증상 | 원인 | 확인 |
|---|---|---|
| `검출 0%` 가 계속 | ROI 안이 비었다 | `ros2 param get /roi_filter roi_x_min` 으로 상자 확인, RViz 로 눈으로 |
| `입력 없음` 경고 | `cluster_median` 이 안 떴다 | `ros2 node list` |
| 검출률이 들쭉날쭉 | 표적이 너무 작거나 멀다 | 위 9.6 표 |
| 위치가 갑자기 튄다 | "가장 큰 군집"이 다른 물체로 옮겨갔다 | `n_cluster` 열, ROI 를 더 좁히기 |
| 속도 최대가 비상식적 | 같은 이유 (군집이 갈아탄 순간) | `flight_2d.png` 속도 그래프의 뾰족한 곳 |

마지막 두 개는 **지금 구조의 한계**다. `cluster_median` 은 매 프레임 가장 큰
군집 하나를 고를 뿐 "직전 프레임의 그것"을 따라가지 않는다. 사람이 ROI 안에
들어오면 드론을 놓치고 사람을 잡는다. 제대로 된 추적(연관 + 게이팅)은
11장 B4 로 미뤄 두었다.

## 11. 앞으로 개발할 것

### 우선순위

```
B1  (B) 방식 솔버          <- 대회에 반드시 필요
B2  rosbag 기록 파이프라인   <- 완료
B3  라이다 2대 구성          <- 완료
B4  센서 융합 트래커
B5  배경 차분
B6  드론 판별 로직
```

### B1. (B) 방식 솔버 — N개 마커, 알려진 좌표

대회는 경기장 좌표계가 이미 정해져 있으므로 (A) 로는 안 된다.

```
입력:  마커의 실제 좌표 3개 이상 + 라이다가 본 좌표
출력:  라이다의 (x, y, yaw)
```

수학은 2D 강체 정합(Umeyama/Kabsch)으로 닫힌 해가 있다. `pose_solve` 에 모드를 추가하면 되고, `marker_fit` 의 검출·기록은 그대로 쓴다.

같이 필요한 것: **`marker_fit` 이 마커 여러 개를 동시에 검출**하도록 확장. 지금은 한 번에 하나만 고른다(ROI 를 옮겨가며 하나씩 재는 것으로 우회 가능).

### B2. rosbag 기록 — **완료**

`record_flight.launch.py` 로 구현했다. 사용법은 9장 참고.

사후 분석으로 가면 **지연 215 ms 문제를 아예 안 건드려도 된다.** 지연은 "사건이
일어나고 내가 알기까지의 시간"인데, 비행 후 분석하면 무의미하다. 타임스탬프만
정확하면 된다.

### B3. 라이다 2대 구성 — **완료**

2026-08-24 에 구성했다. 설치·동시 보정·겹침 확인은 [DUAL_LIDAR.md](DUAL_LIDAR.md) 참고.


- 런치 파일에 `lidar2` 추가 (지금 주석 처리됨)
- 각 라이다별 보정 파일 (`calibration_lidar2.yaml`)
- 같은 마커 3개를 양쪽이 다 보게 하면 **자동으로 정렬**된다

**PoE 스위치 구매 시 확인할 것:**

| 항목 | 요구 |
|---|---|
| 속도 | **기가비트 이상** (라이다 1대가 160 Mbps, 100Mbps 로는 불가) |
| PoE 규격 | **802.3at (PoE+)**. OS1 은 14~20 W 라 802.3af 로는 아슬아슬 |
| 총 전력 | **60 W 이상** (2대 40 W + 여유) |

검토 중인 2.5G / 스위칭 40 Gbps 제품이면 충분하다.

**노트북은 한 대로 충분하다.** 전체 파이프라인이 코어의 41%만 쓴다. 2대여도 82%로 코어 하나 미만이다. 한 대로 가면 시계 동기화·네트워크 설정·PTP 가 전부 불필요해진다.

현장 전원도 챙길 것: 라이다 40 W + 스위치 15 W + 노트북 65 W = **약 120 W**.

### B4. 센서 융합 트래커

두 관측을 **순차 갱신**으로 KF 에 넣는다.

```
predict(t_A까지) -> 센서A로 update -> predict(t_B까지) -> 센서B로 update
```

두 라이다의 회전 위상이 안 맞아 같은 지점을 다른 시각에 훑는데(10 Hz 면 최대 100 ms 차이), 이 방식이면 시간차를 흡수한다. **PTP 로도 안 풀리는 문제**라 이 구조가 필요하다.

`DronePositioningSystem/ros2_ws/.../lidar_drone_tracker_fusion.py` 에 원형이 있으나 `open3d` 의존성 차이로 그대로는 안 돌아간다. 이식하거나 다시 써야 한다.

> **참고:** 라이다가 자기 쪽 면만 보는 편향은 1대에서는 상쇄되지 않는다(물체 깊이의 절반). 2대 직교 배치면 서로 상쇄되어 잔차 0.048 m 까지 줄었다는 실측 기록이 있다.

### B5. 배경 차분

지금은 ROI 를 손으로 맞추는데, 장소가 바뀌면 다시 해야 한다. 또 좌표계가 회전하면 축정렬 박스가 방에 안 맞아 영역을 손해 본다(실측 13~47%).

빈 방을 몇 초 학습해 픽셀별 기준 거리를 저장하고, 이후 **기준보다 뚜렷하게 가까워진 점만** 남긴다. 벽·바닥이 자동으로 빠진다.

클라우드가 `128 x 1024` organized 라 픽셀 인덱스가 살아 있어 구현이 쉽고 빠르다. 다만 `roi_filter._pc2_to_numpy` 가 `skip_nans=True` 로 구조를 뭉개고 있어 그 부분을 손봐야 한다.

공터에서는 벽이 없어 덜 급하지만, 지면 반사를 지우는 데는 여전히 유용하다.

### B6. 드론 판별

지금은 "가장 큰 클러스터"를 고른다. 사람이 영역에 들어오면 그쪽을 따라간다. 크기·높이·속도로 드론만 골라야 한다.
